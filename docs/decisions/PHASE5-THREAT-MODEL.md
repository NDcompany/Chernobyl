## 1. Assets and adversaries

**Assets.** Paired-device PSKs (highest value — they authorize command execution); command/event traffic (can contain secrets the user pastes into prompts); permission-approval flow (an attacker who can approve wins tool execution); the on-disk registry/journal; availability of the companion.

**Adversaries considered.** (a) Network attacker on the same LAN / inside a tunnel path; (b) malicious webpage in the user's browser (CSWSH); (c) malicious local process; (d) stolen/lost paired phone; (e) the tunnel/relay operator as passive observer; (f) brute-force/DoS noise. Not modeled: OS-level compromise of the companion's own user account (defeats DPAPI by construction), physical DMA attacks.

## 3. Verified facts

### 3.1 Auth-mode separation (how the layers compose)

1. **Transport token** (optional on loopback, mandatory off-loopback): `?token=` query **or** `Authorization: Bearer`, both constant-time compared (`server.rs:43-53`). Wrong token → socket upgrades, then Close **4001** (`:283-303`); ≥5 failures → HTTP **429** without upgrading (`:285-290`, limit `:27`); success resets the counter (`:304`).
2. **E2E session** (per-device PSK): `hs_hello → hs_challenge → hs_proof → hs_ok`, fresh server nonce+salt per attempt (`server.rs:703-746`); proof = HMAC-SHA-256 over role‖device_id‖nonce‖salt (`e2e.rs:47-65`), mutual (direction-bound, `e2e.rs:197-199`); handshake rejects expired/spent/unknown/**revoked** devices (`server.rs:399-445`); `hs_err` does **not** close the connection (verified by new test `hs_proof_before_hello_is_rejected_but_connection_survives`).
3. **E2E enforcement is posture-dependent (D2 resolved 2026-10-23):** on **loopback** the parity/dev path is unchanged — with no live session, valid messages (e.g. `prompt_async`) are parsed and executed in **plaintext** and answered unsealed (`server.rs:675-699`, `:810-814`; parity control test `loopback_posture_still_accepts_plaintext_commands` `server.rs:1241-1251`; ADR-010 deviation note; differential A/B depends on it). On a **non-loopback bind** (remote posture — computed once from the same bind predicate as the token requirement, `server.rs:92-107`), every non-exempt message without a live session gets an explicit `ack_err("e2e session required (remote posture)")` — commandId preserved, connection survives so the client can handshake and retry — and is never executed (`server.rs:754-772`); exempt: `Hello` (version gate), `Ping` (liveness), and the `hs_*` handshake itself (`server.rs:703-746`). Beyond loopback a stolen token alone therefore no longer buys command execution — the PSK handshake must complete first. Evidence: `remote_posture_gates_commands_until_the_session_is_handshaken` (`server.rs:1208-1239`) — plaintext command refused → handshake → same command runs sealed.
4. **Version gate:** wrong `hello` version → error ack then Close 4002, ordering guaranteed (`server.rs:774-799`; self-test `main.rs:537-563`). The check requires the `f64` field to be an exact integer equal to `PROTOCOL_VERSION` (`protocol.fract() != 0.0 || *protocol as u32 != PROTOCOL_VERSION`, `server.rs:776-778`) — this closed a verified divergence where the previous `*protocol as u32` cast truncated `2.5` to 2 and passed the Rust gate while TypeScript rejected it. Both implementations now accept only the exact integer version. Server-gate tests over a live connection: `hello_gate_rejects_fractional_and_wrong_versions_with_4002` (`2.5`, older `1`, newer `3` → mismatch ack + Close 4002) and `hello_gate_accepts_the_exact_supported_version` (`server.rs:1076-1119`, supported version → hello_ack, connection stays live); TypeScript pins `2.5` and `1` (`host.test.ts`, `fractional and older protocol versions are rejected with 4002 (D7)`), newer `999` was already covered. Parser-level acceptance of `2.5` as a finite number is unchanged and pinned (`protocol_number_field_follows_is_num_boundaries` `protocol.rs:1058-1069`) — the gate, not the parser, enforces strict equality; non-finite values and non-number types never reach either gate (schema/parse rejects them as malformed). See D7.

### 3.2 E2E handshake and sealed frames (post-compromise scope)

- Per-connection directional keys HKDF-SHA-256 from PSK + fresh random salt (`e2e.rs:31-43`); monotonic per-direction counter as nonce → replay-proof (`e2e.rs:141-168`); AEAD tag failure, counter skip, or non-UTF8 sealed payload **tears the connection down** (`server.rs:675-699`), unlike message-level garbage which only gets a `malformed` ack (`:691-699`; new tests `malformed_message_is_acked_and_connection_survives`, ws/json/e2e truncation sweeps).
- **No X25519 forward secrecy** (documented decision): compromise of a PSK exposes traffic recorded under the salts of sessions that used it. Fresh salt per connection limits blast radius to sessions using that device's PSK. Post-compromise secrecy is **not claimed** (`crypto.rs:11`).
- Handshake proof cannot be replayed elsewhere: bound to the server's fresh nonce + device + role (`e2e.rs:197-207`).

### 3.3 TLS trade-offs

- std-only Rust has no TLS crate; hand-rolling TLS is off the table (ADR-011 Context). Confidentiality/integrity therefore lives in the E2E layer, not the pipe — every transport (LAN, VPN, tunnel) is treated identically.
- **What the wire exposes pre-E2E:** handshake metadata (device_id, proof = HMAC output, nonce/salt), possibly `?token=` in URLs (PRD §11.4 flags URL leakage; ADR-006's motivation), and plaintext parity-mode commands **on loopback** if no E2E handshake is performed (refused beyond loopback — §3.1.3). Sealed frames reveal only lengths/timing.
- Tunnel option (Phase 5′): edge-terminated TLS protects the public hop; the LAN segment companion↔tunnel stays plaintext `ws://`. Acceptable **only** because E2E seals command traffic — this is the stated design (ADR-011 §1-2).

### 3.4 Browser Origin / CSWSH — D1 resolved

- **Origin policy implemented (2026-10-23, `d12bf9e`):** a WS upgrade carrying an `Origin` header is refused **403 before `validate_upgrade`** (`server.rs:264-274`), closing CSWSH in the default config (loopback, token-less, plaintext commands). The policy is "no browsers until the web app" (ADR-011 §5): `Origin` marks a browser-initiated upgrade; non-browser clients (phone app, CLI, differential tooling, soak harness) send none, so nothing else is affected — the control leg of the test proves the identical upgrade without `Origin` still connects (`ws_upgrade_with_origin_header_is_refused_403`, `server.rs:1122-1147`: raw-socket 403 assertion + no-Origin control).
- What the handshake still does **not** do (by design — D1 is the entire Origin surface): `is_websocket_upgrade` checks only Upgrade/Connection/Sec-WebSocket-Key (`ws.rs:99-108`); `validate_upgrade` additionally checks the WebSocket version and key (`ws.rs:161-169`); `authorized` (`server.rs:55-72`) is the only other header consumer.
- Residuals: (a) the 403 path is proven against a raw socket, **not a real browser** (§4); (b) browsers still receive HTTP GET responses on loopback (`/health` counters) — read-only counts, no commands, no WS; (c) when the web app ships (ADR-011 §5), the blanket refusal becomes an Origin allow-list; (d) native React Native clients are expected to send no `Origin` (OkHttp/NSURLSession do not add one) — **unverified on a physical device**; the phone-validation checklist carries the "403 observed → allow-list decision" watch item.

### 3.5 Token handling

- Token value is never logged (all print/format sites inspected; startup logs only the flag `token auth on` / `token auth OFF`, `main.rs:187-197`); compared in constant time.
- `?token=` in query strings can still leak via proxies/history — **ADR-006 (short-lived single-use tickets) is accepted but unimplemented**: zero matches for "ticket" in `*.rs`; the token flow remains the production path. Conflict C1 stays open. See D3.

### 3.6 Revocation

- `companion revoke <id>` flips the registry flag (`main.rs:366-390`); it is enforced **at handshake time** (`server.rs:434-436`).
- A **live** session of a revoked device is **not** terminated — evidence: the revocation test proves only that the *next* handshake fails (`revoking_a_live_device_blocks_reconnect`, `server.rs:1534-1551`), and no code path disconnects existing sessions on revoke (grep: none). A lost-phone attacker keeps an open session until it drops; README:42 already states "at the next handshake". See D4.

### 3.7 Diagnostics exposure — D6 resolved

- `/health` is served on **both** listeners; on the **main listener beyond loopback** (with a token configured) it now requires the token and answers 401 otherwise (`server.rs:251-261` gate, `:336-347` route; test `health_gates_on_the_token_beyond_loopback_but_stays_open_on_loopback` `server.rs:1254-1271` — 401 without token, 200 with `?token=`, diagnostics listener open, loopback open). Loopback and the diagnostics listener keep the open counters-only contract (dev parity; diagnostics is loopback-bound by bind contract). The body is counters only — clients/hosts/sessions/pending/lastSeq/commands/unresolved/events/malformed/storageFailed/uptime/rss (`companion.rs:394-443`); no secrets, no entity contents.
- `/version` and `/adapters` are diagnostics-listener-only (`server.rs:348-360`) → loopback-only by the bind contract.
- Net: binding the main listener non-loopback (with a token — required at startup) no longer exposes counters to the network — same posture as the WS gate.

### 3.8 Abuse hardening (implementation verified; test coverage varies)

**Test-covered** (asserted in-suite): payload cap 256 000 B checked **before allocation** (`ws.rs:9`, `:270` — exact boundary pinned by `payload_size_boundaries_at_cap_and_length_marker_edges`); handshake cap 16 KiB (`ws.rs:10`, test `handshake_size_cap` `ws.rs:357-365`); ≤64 headers, colon-required lines (`ws.rs:136-151`, boundary tests added); hostile corpora for JSON/frames/handshake/client messages (this session: truncation sweeps, LCG stress, close-payload boundaries — 16 new tests).

**Implemented and verified in source, but NOT covered by any identified test** (no test coverage implied): heartbeat read timeout + miss-limit (`server.rs:600`, `:641-647`); 30 s handshake read timeout (`server.rs:241`); auth-failure 429 pre-upgrade path (`server.rs:285-290`, limit `:27`, counter reset on success `:304`) — only the 4001 wrong-token close has test coverage (`main.rs:514-530`) — though the soak harness now exercises the 429 path end-to-end (6th consecutive bad token → HTTP 429, recovery after reset; `unauthorized_accepted` criterion, smoke green). The auth-failure counter is **global** (shared across all connections), not per-IP — parity with the Node host; a per-IP counter is a Phase 5′ consideration, not changed here.

**Availability / outbound resources — D8 resolved (2026-10-23):** each connection's outbound queue is bounded by message count **and** total payload bytes — 256 messages / 4 MiB (`server.rs:39-41`; 4 MiB = 16× the 256 000-B frame cap, typical event/ack frames are a few KB) — and every socket write (data and control frames share the socket options) carries a 10 s write timeout. Saturation is never a silent drop: `Outbound::enqueue` fails and marks the connection terminated (`server.rs:481-562`); engine broadcasts use the same non-blocking enqueue, so a saturated peer is deregistered without parking the engine or the registry lock (`companion.rs:104-112`); the read loop checks the terminated flag before handling any inbound frame and on the heartbeat path, tearing the socket down within one frame or one beat (`server.rs:645`, `:662`). Writer failure (write error, stalled-peer timeout, peer reset) exits the writer thread; its dropped receiver surfaces `Disconnected` to every producer, and teardown's `join()` is bounded by the write timeout — no thread can leak. Reliability boundary (no guarantee invented): the server guarantees FIFO handoff to the socket **or** an observable close — never client receipt; TCP close can discard buffered data, and protocol v2 has no per-message application acknowledgements for events, so clients resync state via the hello snapshot after reconnect. Evidence: 9 deterministic tests (`server.rs:1273-1465`) — queue count/byte bounds, byte release on dequeue, FIFO ordering, disconnect propagation, writer wire-order/exit-on-drop/termination-on-reset, a live saturation-teardown integration test, and a sequential-reply ordering regression. A pre-existing teardown leak (fallible socket setup running after registration could strand the registry entry and the writer thread) was fixed in the same change (`server.rs:586-602`). End-to-end harness evidence (2026-10-23, `npm run soak:smoke`, harness `tools/soak.mjs` committed `032257d`): both saturation paths reproduced over real sockets against the current binary — a stopped-consuming client was torn down in **533 ms** (count-bound path, 8 107-B replies) and **542 ms** (byte-bound path, 38 334-B replies, `expected bound: bytes` chosen adaptively from measured reply size vs the 4 MiB/256 = 16 KiB threshold); silent dead-peer released at **62 s** (heartbeat bound 15 s × 3 misses + slack); churn, abrupt-death and quiesce phases all returned the client gauge to 0; graceful `--exit-after` shutdown with live clients and queued work exited 0 and logged its shutdown sequence; restart on the same data dir served reconnecting clients 2/2; RSS 4.9 → 6.7 MiB over the run. Threshold provenance is stated in every summary.json (existing source limits vs newly proposed soak limits: 64 MiB quiesced-growth, 512 MiB absolute, release timeouts above the source-derived teardown bounds).

### 3.9 Endpoint list trust boundaries — advertisement + ordered reconnect built (S10, 2026-10-23)

**Built (ADR-011 §2):** `--endpoint` is repeatable — every flag lands in the QR `ep` array in CLI order (no `--endpoint` → the bind address alone, `main.rs` pair_main); the app's transport dials the list **in order**: each attempt that never reached a session advances to the next endpoint, a drop after a live session restarts the cycle at the primary, an explicit `connect()` resets to the primary (`packages/e2e/src/transport.ts`). No discovery scheme of any kind exists: the operator's CLI order IS the order, nothing is probed or re-ranked.

**Security review (ordering / downgrade / replay):**
- **Ordering** — the list is advisory dial order, honored exactly as printed. Reordering gains an attacker nothing: every endpoint is dialed under the same E2E handshake, so there is no "cheaper to MITM" position in the list.
- **Downgrade / substitution** — stripping, truncating or replacing `ep` entries is an **availability** attack only. A substituted endpoint cannot complete the handshake: `hs_ok` requires a server proof computed under the device PSK, so an impostor fails as `server-proof-mismatch`, which the client treats as **terminal deny** (no rotation into an attacker-chosen endpoint, no retry loop); an unresponsive substitute times out and the client fails over to the next entry. Substituting *all* entries ends in the same terminal deny. No confidentiality or command-integrity loss is reachable from tampering with the list — only a client that already holds the PSK can reach `connected` (evidence: interop wrong-PSK + S10 failover checks, `tools/e2e-interop.mjs`).
- **Replay** — the endpoint list is **not a credential**: it carries no secret, and a captured QR payload replayed later (with its list) is rejected by the existing PSK/challenge/expiry/single-use gates (`server.rs` establish_session; matrix test `s3`). Replaying only the list (no payload) yields exactly nothing: dialing an address the attacker already controls is covered by the substitution case above.
- **Capacity edge (documented):** QR v10-M caps the payload at 213 bytes — two `ws://127.0.0.1:<4-digit>` entries fit exactly; longer lists (e.g. LAN + DDNS) overflow. The CLI prints the `payload:` line **before** attempting the QR, so overflow (exit 1 + clear error) still yields a pasteable credential; the app's paste path accepts it unchanged. Proven: interop checks "multi-endpoint QR payload keeps CLI order" and "QR overflow keeps a pasteable payload with endpoint order intact".
- **Residual (unchanged):** default deployment still exposes no non-loopback listener and integrates no tunnel; the endpoint list advertises nothing an operator did not explicitly pass. Ordered reconnect proves failover + order (unit + interop), not reachability from any particular network — actual remote reachability (tailnet/DDNS/tunnel) stays a deployment how-to (`services/companion-rs/README.md`), untested here.

## 4. Unverified assumptions (explicitly not proven)

- **No external/independent security audit** (TODO:246-247 — the hostile-input corpus + KATs are the only adversarial evidence).
- Constant-time behavior of `ct_eq`/Poly1305 arithmetic is by construction, **never measured** by side-channel instrumentation.
- No fuzzing, Miri, ASAN/UBSAN, or Haskell-style property harness ran over the hand-rolled crypto/framing; determinism evidence is the seeded corpora only.
- DPAPI assumes the Windows user-profile boundary; same-user code can unprotect PSKs (by design of DPAPI).
- D1's 403 refusal is proven against a raw socket, not a real browser, and native-Android-sends-no-`Origin` is source-reasoned (OkHttp/NSURLSession defaults), not device-verified — both are carried as watch items in `docs/validation/PHONE-VALIDATION-CHECKLIST.md` §8/known-risks.
- Malicious-local-process adversary in loopback-no-token mode is accepted in dev parity mode; not a claim for production posture.

## 5. Decisions (D1/D2/D6 resolved 2026-10-23 by the Phase 5′ release-readiness campaign; D3 re-scheduled via ADR-013, D4 recommendation in ADR-014 awaiting owner ratification, D5 remains with the product owner)

- **D1 — RESOLVED (2026-10-23, `d12bf9e`).** Policy: **no browsers until the web app** — any WS upgrade carrying an `Origin` header is refused 403 before the handshake (`server.rs:264-274`); when the web app ships (ADR-011 §5) this becomes an Origin allow-list. Rationale: implements the documented no-web-UI posture (ADR-011 §5) and closes CSWSH in the default loopback/token-less config without inventing an allow-list prematurely; no current client sends `Origin` (differential `ws` tooling and the Rust `WsClient` proven by test; mobile native only source-reasoned). Evidence: `ws_upgrade_with_origin_header_is_refused_403` (`server.rs:1122-1147`) — 403 asserted, no-Origin control still connects. Residual risks: real-browser and real-device behavior untested (checklist known-risks); HTTP GETs remain answered on loopback (read-only counters).
- **D2 — RESOLVED (2026-10-23, `d12bf9e`).** Synthesized resolution (no explicit PRD/ADR recommendation existed — this is documented campaign policy, not a doc mandate): **enforce `e2e.is_some()` before non-handshake messages on non-loopback binds only** (remote posture = the same bind predicate as `main.rs`'s token requirement), with `Hello`/`Ping`/`hs_*` exempt; refusals are `ack_err` with the commandId preserved and the connection left alive for handshake recovery (`server.rs:754-772`). Loopback keeps the documented parity/dev plaintext path (ADR-010 deviation note; differential A/B unchanged). Effect: beyond loopback a stolen token is no longer sufficient for command execution — the PSK handshake must complete first. Residual risks (explicit): (a) loopback remains token-gated-only by design (dev parity; adversary (c) accepted); (b) the mobile client has no `hs_*` code yet, so a phone cannot use remote posture until Phase 6; (c) enforcement is bind-based — a tunnel deployment that keeps the companion on loopback inherits the parity posture (acceptable: same-host case). Evidence: `remote_posture_gates_commands_until_the_session_is_handshaken` + parity control `loopback_posture_still_accepts_plaintext_commands` (`server.rs:1208-1251`).
- **D3 — RESOLVED-as-rescheduled (2026-10-23, ADR-013).** ADR-006 ticket migration formally re-scheduled to the web-app milestone with an interim statement: the long-lived query token stays the production *connection-admission* credential only — beyond loopback commands still require the PSK-derived E2E session (D2), the PSK never travels in a URL, and the residual accepted risk is connection-spam / counters-only `/health` reads, not command execution. Deferral is the conservative direction (no code/wire change, reversible by implementing ADR-006 unchanged). Evidence: `ADR-013-ticket-migration-rescheduled.md`.
- **D4 — RECOMMENDATION (2026-10-23, ADR-014), not yet ratified/implemented.** Recommend **terminate-on-revoke**, implemented via an in-process revoke path to the running companion (close code 4003 mirroring 4001/4002 as terminal deny), *not* a journal tail-watcher (two processes sharing one append journal is a latent hazard; a watcher adds Windows rename-over-open-handle races for no security win). Not implemented: reserved to product owner, would flip a frozen interop-asserted semantic, and the 24 h soak is running on a frozen binary. Honest exposure (verified): revocation applies at the next handshake *after restart*; a live session of a revoked device is never terminated — bounded ≤ ~45 s for a silent peer (heartbeat 15 s × 3 misses) but **unbounded for an active attacker** who answers heartbeats. Evidence: `ADR-014-revocation-live-sessions.md`, interop scenario 7 (`e2e-interop.mjs:312-335`), `revoking_a_live_device_blocks_reconnect` (`server.rs:1534-1551`).
- **D5 — Transport TLS:** accept edge-terminated tunnel TLS + E2E as the complete story (ADR-011) vs revisit if a first-party hosted relay ever enters scope. std-only constraint makes native TLS impossible without changing ADR-010.
- **D6 — RESOLVED (2026-10-23, `d12bf9e`).** Gate main-listener `/health` behind the token when bound beyond loopback **and** a token is configured (401 otherwise; `?token=` accepted via the existing `authorized()`); loopback and the loopback-bound diagnostics listener keep open counters (dev parity + PRD §15.2 contract). Consistent with the non-loopback=hardened architecture; the body stays counts-only either way. Evidence: `health_gates_on_the_token_beyond_loopback_but_stays_open_on_loopback` (`server.rs:1254-1271`).
- **D7 — RESOLVED (2026-10-23).** Strict equality is the accepted rule: the Rust gate rejects any `hello.protocol` that is not the exact integer `PROTOCOL_VERSION` (fractional check before the cast comparison, `server.rs:776-778`), matching TypeScript's unchanged strict `!==` (`services/host/src/host.ts:85`). Evidence: server-gate tests over a live connection assert mismatch ack + Close 4002 for `2.5` (the truncation case), older `1`, newer `3`, and hello_ack + live connection for the supported version (`server.rs:1076-1119`); the TS suite pins `2.5` and `1` (`host.test.ts`, newer `999` pre-existing). Suites green post-change: Rust 147 passed / 0 failed / 3 ignored + self-test, clippy/fmt clean; TS host 22/22 + `tsc` clean. Parser-side acceptance unchanged and pinned (`protocol.rs:1058-1069`) — the gate enforces equality, the parser enforces finite-number shape, so non-finite/malformed values stay on the malformed path on both sides. Mobile stance documented: no version negotiation — the app pins `PROTOCOL_VERSION` from `@chernobyl/protocol`, so a future version bump requires companion and app to move together (strict reject otherwise).
- **D8 — RESOLVED (2026-10-23).** Bounded-queue policy implemented: 256 messages **and** 4 MiB of queued payload per connection, plus a 10 s socket write timeout (`server.rs:39-41`). Overflow policy is explicit teardown, never a silent drop — `enqueue` marks the connection terminated on count/byte saturation or writer death (`server.rs:481-562`); read-loop producers (handshake replies, acks, pongs, malformed acks) break into the existing teardown path, engine broadcasts deregister the peer non-blockingly (`companion.rs:104-112`), and the read loop closes the socket on its next frame or heartbeat tick (`server.rs:645`, `:662`). Writer death propagates as `Disconnected` to all producers; teardown `join()` is bounded (write timeout), so no thread leaks; all producers are non-blocking (`try_send`), so no deadlock exists between engine, registry lock and writer. Ordering preserved (single FIFO per connection); wire format unchanged (TS untouched). Reliability boundary documented in §3.8. Evidence: 9 deterministic tests (`server.rs:1273-1465`) incl. live saturation teardown + FIFO regression; Rust 156 passed / 0 failed / 3 ignored + self-test ALL CHECKS PASSED, clippy `-D warnings`/fmt clean; TS host 22/22 unchanged; soak-harness end-to-end teardowns (533 ms count-path / 542 ms byte-path) in §3.8.
