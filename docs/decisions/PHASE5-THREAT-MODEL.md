## 1. Assets and adversaries

**Assets.** Paired-device PSKs (highest value — they authorize command execution); command/event traffic (can contain secrets the user pastes into prompts); permission-approval flow (an attacker who can approve wins tool execution); the on-disk registry/journal; availability of the companion.

**Adversaries considered.** (a) Network attacker on the same LAN / inside a tunnel path; (b) malicious webpage in the user's browser (CSWSH); (c) malicious local process; (d) stolen/lost paired phone; (e) the tunnel/relay operator as passive observer; (f) brute-force/DoS noise. Not modeled: OS-level compromise of the companion's own user account (defeats DPAPI by construction), physical DMA attacks.

## 3. Verified facts

### 3.1 Auth-mode separation (how the layers compose)

1. **Transport token** (optional on loopback, mandatory off-loopback): `?token=` query **or** `Authorization: Bearer`, both constant-time compared (`server.rs:43-53`). Wrong token → socket upgrades, then Close **4001** (`:283-303`); ≥5 failures → HTTP **429** without upgrading (`:285-290`, limit `:27`); success resets the counter (`:304`).
2. **E2E session** (per-device PSK): `hs_hello → hs_challenge → hs_proof → hs_ok`, fresh server nonce+salt per attempt (`server.rs:837-886`); proof = HMAC-SHA-256 over role‖device_id‖nonce‖salt (`e2e.rs:47-65`), mutual (direction-bound, `e2e.rs:197-199`); handshake rejects expired/spent/unknown/**revoked** devices (`establish_session` `server.rs:486-558`); `hs_err` does **not** close the connection (verified by new test `hs_proof_before_hello_is_rejected_but_connection_survives`).
3. **E2E enforcement is posture-dependent (D2 resolved 2026-10-23):** on **loopback** the parity/dev path is unchanged — with no live session, valid messages (e.g. `prompt_async`) are parsed and executed in **plaintext** and answered unsealed (inbound plaintext branch `server.rs:820-828`, `enqueue_sealed` passes through when no session `server.rs:628-653`; parity control test `loopback_posture_still_accepts_plaintext_commands` `server.rs:1416-1426`; ADR-010 deviation note; differential A/B depends on it). On a **non-loopback bind** (remote posture — computed once from the same bind predicate as the token requirement, `server.rs:92-107`), every non-exempt message without a live session gets an explicit `ack_err("e2e session required (remote posture)")` — commandId preserved, connection survives so the client can handshake and retry — and is never executed (`server.rs:895-905`); exempt: `Hello` (version gate), `Ping` (liveness), and the `hs_*` handshake itself (`server.rs:837-886`). Beyond loopback a stolen token alone therefore no longer buys command execution — the PSK handshake must complete first. Evidence: `remote_posture_gates_commands_until_the_session_is_handshaken` (`server.rs:1383-1414`) — plaintext command refused → handshake → same command runs sealed.
4. **Version gate:** wrong `hello` version → error ack then Close 4002, ordering guaranteed (`server.rs:774-799`; self-test `main.rs:537-563`). The check requires the `f64` field to be an exact integer equal to `PROTOCOL_VERSION` (`protocol.fract() != 0.0 || *protocol as u32 != PROTOCOL_VERSION`, `server.rs:776-778`) — this closed a verified divergence where the previous `*protocol as u32` cast truncated `2.5` to 2 and passed the Rust gate while TypeScript rejected it. Both implementations now accept only the exact integer version. Server-gate tests over a live connection: `hello_gate_rejects_fractional_and_wrong_versions_with_4002` (`2.5`, older `1`, newer `3` → mismatch ack + Close 4002) and `hello_gate_accepts_the_exact_supported_version` (`server.rs:1076-1119`, supported version → hello_ack, connection stays live); TypeScript pins `2.5` and `1` (`host.test.ts`, `fractional and older protocol versions are rejected with 4002 (D7)`), newer `999` was already covered. Parser-level acceptance of `2.5` as a finite number is unchanged and pinned (`protocol_number_field_follows_is_num_boundaries` `protocol.rs:1058-1069`) — the gate, not the parser, enforces strict equality; non-finite values and non-number types never reach either gate (schema/parse rejects them as malformed). See D7.

### 3.2 E2E handshake and sealed frames (post-compromise scope)

- Per-connection directional keys HKDF-SHA-256 from PSK + fresh random salt (`e2e.rs:31-43`); monotonic per-direction counter as nonce → replay-proof (`e2e.rs:141-168`); AEAD tag failure, counter skip, or non-UTF8 sealed payload **tears the connection down** (`server.rs:809-829`), unlike message-level garbage which only gets a `malformed` ack (`send_malformed` `server.rs:993-1000`, now sealed for session clients per §3.10; tests `malformed_message_is_acked_and_connection_survives`, ws/json/e2e truncation sweeps).
- **No X25519 forward secrecy** (documented decision): compromise of a PSK exposes traffic recorded under the salts of sessions that used it. Fresh salt per connection limits blast radius to sessions using that device's PSK. Post-compromise secrecy is **not claimed** (`crypto.rs:11`).
- Handshake proof cannot be replayed elsewhere: bound to the server's fresh nonce + device + role (`e2e.rs:197-207`).

### 3.3 TLS trade-offs

- std-only Rust has no TLS crate; hand-rolling TLS is off the table (ADR-011 Context). Confidentiality/integrity therefore lives in the E2E layer, not the pipe — every transport (LAN, VPN, tunnel) is treated identically.
- **What the wire exposes pre-E2E:** handshake metadata (device_id, proof = HMAC output, nonce/salt), possibly `?token=` in URLs (PRD §11.4 flags URL leakage; ADR-006's motivation), and plaintext parity-mode commands **on loopback** if no E2E handshake is performed (refused beyond loopback — §3.1.3). Sealed frames reveal only lengths/timing.
- Tunnel option (Phase 5′): edge-terminated TLS protects the public hop; the LAN segment companion↔tunnel stays plaintext `ws://`. Acceptable **only** because E2E seals command traffic — this is the stated design (ADR-011 §1-2).

### 3.4 Browser Origin / CSWSH — D1 resolved

- **Origin policy implemented (2026-10-23, `d12bf9e`):** a WS upgrade carrying an `Origin` header is refused **403 before `validate_upgrade`** (`server.rs:264-274`), closing CSWSH in the default config (loopback, token-less, plaintext commands). The policy is "no browsers until the web app" (ADR-011 §5): `Origin` marks a browser-initiated upgrade; non-browser clients (phone app, CLI, differential tooling, soak harness) send none, so nothing else is affected — the control leg of the test proves the identical upgrade without `Origin` still connects (`ws_upgrade_with_origin_header_is_refused_403`, `server.rs:1122-1147`: raw-socket 403 assertion + no-Origin control).
- What the handshake still does **not** do (by design — D1 is the entire Origin surface): `is_websocket_upgrade` checks only Upgrade/Connection/Sec-WebSocket-Key (`ws.rs:99-108`); `validate_upgrade` additionally checks the WebSocket version and key (`ws.rs:161-169`); `authorized` (`server.rs:55-72`) is the only other header consumer.
- Residuals: (a) the 403 path is proven against a raw socket, **not a real browser** (§4); (b) browsers still receive HTTP GET responses on loopback (`/health` counters) — read-only counts, no commands, no WS; (c) when the web app ships (ADR-011 §5), the blanket refusal becomes an Origin allow-list; (d) native React Native clients are expected to send no `Origin` (OkHttp/NSURLSession do not add one) — **unverified on a physical device**; the phone-validation checklist carries the "403 observed → allow-list decision" watch item.

### 3.5 Token handling

- Token value is never logged (all print/format sites inspected; startup logs only the flag `token auth on` / `token auth OFF`, `main.rs:187-197`); compared in constant time.
- `?token=` in query strings can still leak via proxies/history — **ADR-006 (short-lived single-use tickets) is accepted but unimplemented**: zero matches for "ticket" in `*.rs`; the token flow remains the production path. Conflict C1 stays open. See D3.

### 3.6 Revocation — D4 resolved (2026-10-25)

- `companion revoke <id>` routes to the running companion via `POST /devices/revoke` on the loopback diagnostics listener, falling back to an offline journal write if the companion is unreachable. Handshakes continue to fail closed (`hs_err device revoked`, `server.rs`).
- **Live sessions are terminated immediately (D4 terminate-on-revoke):** The running companion marks the device `revoked` in its store, appends an audit record, and terminates every live connection whose session belongs to that device with WebSocket close code **4003** (`CLOSE_DEVICE_REVOKED`, reason `"device revoked"`). Teardown runs through the existing RAII guard (`ConnGuard`), cleaning up registry entries and stopping the writer thread.
- Browser protection: `POST /devices/revoke` rejects requests with an `Origin` header (403, matching D1 posture) and is absent on the main listener (404).
- The lost-phone open-session gap is closed. Evidence: `revocation_route_terminates_live_session_leaves_others_intact_and_blocks_reconnect`, `revocation_route_rejects_origin_header_with_403`, `revocation_route_is_absent_on_main_listener`, `revocation_route_returns_404_for_unknown_device_and_400_for_malformed_body`, and `cli_revoke_offline_falls_back_and_online_routes_to_running_companion`.

### 3.7 Diagnostics exposure — D6 resolved

- `/health` is served on **both** listeners; on the **main listener beyond loopback** (with a token configured) it now requires the token and answers 401 otherwise (`server.rs:251-261` gate, `:336-347` route; test `health_gates_on_the_token_beyond_loopback_but_stays_open_on_loopback` `server.rs:1254-1271` — 401 without token, 200 with `?token=`, diagnostics listener open, loopback open). Loopback and the diagnostics listener keep the open counters-only contract (dev parity; diagnostics is loopback-bound by bind contract). The body is counters only — clients/hosts/sessions/pending/lastSeq/commands/unresolved/events/malformed/storageFailed/uptime/rss (`companion.rs:394-443`); no secrets, no entity contents.
- `/version` and `/adapters` are diagnostics-listener-only (`server.rs:348-360`) → loopback-only by the bind contract.
- Net: binding the main listener non-loopback (with a token — required at startup) no longer exposes counters to the network — same posture as the WS gate.

### 3.8 Abuse hardening (implementation verified; test coverage varies)

**Test-covered** (asserted in-suite): payload cap 256 000 B checked **before allocation** (`ws.rs:9`, `:270` — exact boundary pinned by `payload_size_boundaries_at_cap_and_length_marker_edges`); handshake cap 16 KiB (`ws.rs:10`, test `handshake_size_cap` `ws.rs:357-365`); ≤64 headers, colon-required lines (`ws.rs:136-151`, boundary tests added); hostile corpora for JSON/frames/handshake/client messages (this session: truncation sweeps, LCG stress, close-payload boundaries — 16 new tests).

**Implemented and verified in source, but NOT covered by any identified test** (no test coverage implied): heartbeat read timeout + miss-limit (`server.rs:600`, `:641-647`); 30 s handshake read timeout (`server.rs:241`); auth-failure 429 pre-upgrade path (`server.rs:285-290`, limit `:27`, counter reset on success `:304`) — only the 4001 wrong-token close has test coverage (`main.rs:514-530`) — though the soak harness now exercises the 429 path end-to-end (6th consecutive bad token → HTTP 429, recovery after reset; `unauthorized_accepted` criterion, smoke green). The auth-failure counter is **global** (shared across all connections), not per-IP — parity with the Node host; a per-IP counter is a Phase 5′ consideration, not changed here.

**Availability / outbound resources — D8 resolved (2026-10-23):** each connection's outbound queue is bounded by message count **and** total payload bytes — 256 messages / 4 MiB (`server.rs:39-41`; 4 MiB = 16× the 256 000-B frame cap, typical event/ack frames are a few KB) — and every socket write (data and control frames share the socket options) carries a 10 s write timeout. Saturation is never a silent drop: `Outbound::enqueue` fails and marks the connection terminated (`server.rs:481-562`); engine broadcasts use the same non-blocking enqueue, so a saturated peer is deregistered without parking the engine or the registry lock (`companion.rs:104-112`); the read loop checks the terminated flag before handling any inbound frame and on the heartbeat path, tearing the socket down within one frame or one beat (`server.rs:645`, `:662`). Writer failure (write error, stalled-peer timeout, peer reset) exits the writer thread; its dropped receiver surfaces `Disconnected` to every producer, and teardown's `join()` is bounded by the write timeout — no thread can leak. Reliability boundary (no guarantee invented): the server guarantees FIFO handoff to the socket **or** an observable close — never client receipt; TCP close can discard buffered data, and protocol v2 has no per-message application acknowledgements for events, so clients resync state via the hello snapshot after reconnect. Evidence: 9 deterministic tests (`server.rs:1273-1465`) — queue count/byte bounds, byte release on dequeue, FIFO ordering, disconnect propagation, writer wire-order/exit-on-drop/termination-on-reset, a live saturation-teardown integration test, and a sequential-reply ordering regression. A pre-existing teardown leak (fallible socket setup running after registration could strand the registry entry and the writer thread) was fixed in the same change (`server.rs:586-602`). End-to-end harness evidence (2026-10-23, `npm run soak:smoke`, harness `tools/soak.mjs` committed `032257d`): both saturation paths reproduced over real sockets against the current binary — a stopped-consuming client was torn down in **533 ms** (count-bound path, 8 107-B replies) and **542 ms** (byte-bound path, 38 334-B replies, `expected bound: bytes` chosen adaptively from measured reply size vs the 4 MiB/256 = 16 KiB threshold); silent dead-peer released at **62 s** (heartbeat bound 15 s × 3 misses + slack); churn, abrupt-death and quiesce phases all returned the client gauge to 0; graceful `--exit-after` shutdown with live clients and queued work exited 0 and logged its shutdown sequence; restart on the same data dir served reconnecting clients 2/2; RSS 4.9 → 6.7 MiB over the run. Threshold provenance is stated in every summary.json (existing source limits vs newly proposed soak limits: 64 MiB quiesced-growth, 512 MiB absolute, release timeouts above the source-derived teardown bounds).

### 3.9 Endpoint list trust boundaries — advertisement + ordered reconnect built (S10, 2026-10-23)

**Built (ADR-011 §2):** `--endpoint` is repeatable — every flag lands in the QR `ep` array in CLI order (no `--endpoint` → the bind address alone, `main.rs` pair_main); the app's transport dials the list **in order**: each attempt that never reached a session advances to the next endpoint, a drop after a live session restarts the cycle at the primary, an explicit `connect()` resets to the primary (`packages/e2e/src/transport.ts`). No discovery scheme of any kind exists: the operator's CLI order IS the order, nothing is probed or re-ranked.

**Security review (ordering / downgrade / replay):**
- **Ordering** — the list is advisory dial order, honored exactly as printed. Reordering gains an attacker nothing: every endpoint is dialed under the same E2E handshake, so there is no "cheaper to MITM" position in the list.
- **Downgrade / substitution** — stripping, truncating or replacing `ep` entries is an **availability** attack only. A substituted endpoint cannot complete the handshake: `hs_ok` requires a server proof computed under the device PSK, so an impostor fails as `server-proof-mismatch`, which the client treats as **terminal deny** (no rotation into an attacker-chosen endpoint, no retry loop); an unresponsive substitute times out and the client fails over to the next entry. Substituting *all* entries ends in the same terminal deny. No confidentiality or command-integrity loss is reachable from tampering with the list — only a client that already holds the PSK can reach `connected` (evidence: interop wrong-PSK + S10 failover checks, `tools/e2e-interop.mjs`).
- **Replay** — the endpoint list is **not a credential**: it carries no secret. Replaying only the list (no payload) yields exactly nothing: dialing an address the attacker already controls is covered by the substitution case above. **Correction 2026-10-26:** this bullet used to claim that a captured QR payload replayed later is rejected by the PSK/challenge/expiry/single-use gates. That was wrong: redemption registered the device under the QR's own PSK, so the payload replayed at any later time connected as that device (emulator row 2.2). Since the device key rotation at first use (§3.11), a payload replayed after the paired phone has acked its device key is refused; the window before that ack is a residual (§3.11).
- **Capacity edge (documented):** QR v10-M caps the payload at 213 bytes — two `ws://127.0.0.1:<4-digit>` entries fit exactly; longer lists (e.g. LAN + DDNS) overflow. The CLI prints the `payload:` line **before** attempting the QR, so overflow (exit 1 + clear error) still yields a pasteable credential; the app's paste path accepts it unchanged. Proven: interop checks "multi-endpoint QR payload keeps CLI order" and "QR overflow keeps a pasteable payload with endpoint order intact".
- **Residual (unchanged):** default deployment still exposes no non-loopback listener and integrates no tunnel; the endpoint list advertises nothing an operator did not explicitly pass. Ordered reconnect proves failover + order (unit + interop), not reachability from any particular network — actual remote reachability (tailnet/DDNS/tunnel) stays a deployment how-to (`services/companion-rs/README.md`), untested here.

### 3.10 Post-integration findings (Phase 6/7/8, reassessed 2026-10-24)

After the mobile E2E client, adapters, and TUI shipped, the model was re-walked against the *shipped* code rather than the pre-integration tree. Two findings:

**Finding 1 — side-channel/outbound frames were not sealed for session clients (contract bug — FIXED).** The wire contract (`services/companion-rs/README.md`: "from `hs_ok` on every frame is sealed") was only enforced on the direct reply path; the engine's event fan-out enqueued **plaintext to every registered connection** (registration happens at connect, pre-handshake), and side-channel frames (`malformed` acks) were enqueued plaintext even for a client with a live E2E session. Consequences: (a) a paired phone's `handleSealed` (`packages/e2e/src/transport.ts`) has no plaintext fallback — an unsealed event made it fail `open()` and tear the socket down, so any event churned a real session (interop scenario 2's "no churn" check could mask this via transparent reconnect); (b) an event delivered to a token-holder who had *not* handshaked arrived readable in plaintext at remote posture.

Fix (single root cause): the live E2E session moved from a read-loop-local variable into the per-connection `Outbound` (`server.rs:582`, installed by `set_session` on `hs_ok`), and one sealing point `Outbound::enqueue_sealed` (`server.rs:628-653`) now seals — under the session lock, so the AEAD counter order always matches the FIFO wire order — every outbound producer: reply path (`server.rs:953`), event fan-out (`companion.rs:140`), and `malformed` acks (`send_malformed` → `server.rs:993`). A completeness sweep then sealed the one producer that writes *directly* to the socket rather than through `Outbound`: the protocol-mismatch ack in the D7 version gate (`server.rs:921-932`) — it is written synchronously to guarantee ack-before-close ordering, and the mobile app sends its `hello` *after* the handshake, so a version-drift reaches this path with a live session; it is now sealed under the session lock (plaintext `ack.clone()` when no session, so the plaintext D7 tests are unaffected). With no session `enqueue_sealed` passes the plaintext through verbatim, so loopback dev parity (ADR-010) and the differential/soak/TUI plaintext paths stay byte-identical. Lock ordering has no cycle (fan-out takes `clients`→`session`; the read loop takes `session` alone, never `session`→`clients`). Pre-session frames by definition seal nothing (`enqueue_sealed` sees `None`). Evidence: new tests `fanout_event_to_session_client_is_sealed` (`server.rs:1199`) — a watcher with its own session receives the fanned-out `session_created` **sealed** and openable (a plaintext event fails `open()` and panics the test) — and `hello_gate_mismatch_ack_is_sealed_for_a_session_client` (`server.rs:1311`) — a session client's version-drifted sealed `hello` yields a **sealed** mismatch ack openable via the session before the close-4002; full gates green (Rust 186 passed / 0 failed / 4 ignored, clippy `-D warnings`, fmt, `npm run verify` exit 0, interop 17/17 PASS, soak smoke 10/10 PASS).

**Finding 2 — pre-session `Hello` returns a full snapshot at remote posture (authorization-semantics conflict — D9, deferred, no code change).** `require_e2e` exempts `Hello` (`server.rs:884-905`), and that pre-session `Hello` returns `companion.snapshot()` — hosts/addresses, sessions, permission prompts, activity text — in plaintext to anyone holding only the transport token. This contradicts ADR-013's wording that the long-lived token is a *connection-admission* credential only (with counters-only residual), while the phone checklist row 1.2 (`PHONE-VALIDATION-CHECKLIST.md`) *expects* a token-only `hello` → `hello_ack` with a snapshot (token = read-only dashboard + admission), and the README promises "every `hello` returns a full snapshot." The internal documents conflict, so this is documented as **D9** (§5) with both options and a recommendation, not silently gated — same pattern as D4 (owner ratification required). No code change made; the mobile client always handshakes *first* then sends a sealed `hello` (`packages/e2e/src/transport.ts:240-272`), so a compliant paired phone never depends on the pre-session snapshot.

### 3.11 Pairing-QR replay: device key rotation at first use (2026-10-26)

**Finding (emulator row 2.2, 2026-10-25).** `redeem` registered the device under the same PSK the QR carries, so the QR payload stayed a valid credential for as long as the device stayed unrevoked: after `pm clear`, the same payload paired again ("2 hosts online"). `spent_pairing_cannot_be_reused` only covered an artificial state (offer consumed, no device record), and §3.9 claimed a replayed payload was rejected. The realistic threat: someone photographs or screenshots the QR during its 5-minute display, or finds the payload later (a screenshot, the clipboard, a shared pairing link), and gets persistent access as the device.

**Fix (ADR-011 addendum).** The first redemption mints a fresh 32-byte device key `K_dev` (CSPRNG FFI) and stores it DPAPI-protected as the device record's `pskNext`, beside the QR's PSK. Right after `hs_ok`, while that key is pending, the server sends one sealed transport-level frame `{"type":"hs_rekey","psk":"<b64 K_dev>"}`: the same key on every connection until it is promoted, never a new mint. The phone persists it in the keystore, and only then answers with the sealed `{"type":"hs_rekey_ack"}` and proves `K_dev` from its next handshake on. The ack promotes `K_dev` to the device's only key under the storage lock. The handshake verifies against the current key and, while one is pending, the next one: a proof under the next key means the phone stored it but the ack was lost, and `redeem` promotes it atomically when it re-decides under the lock (the verify-unlocked, decide-again-locked invariant is unchanged). After promotion the QR's PSK fails the proof: `hs_err`, which the client already treats as a terminal deny (no retry loop). This is a two-phase commit, so a lost `hs_rekey` (the phone keeps the old key and is offered the key again), a failed keystore write (no ack, old key kept) and a lost ack (the next handshake promotes) all leave both ends with a working key. The ack counts only inside a session. Revocation, including the live 4003 close, is unchanged: a revoked device is refused under either key and nothing promotes its pending key. Neither key is ever logged, and the journal holds both only DPAPI-protected.

Evidence: `replayed_qr_after_pairing_is_refused`, `lost_rekey_ack_promotes_on_next_handshake_with_new_key`, `client_ignoring_rekey_keeps_working_and_is_offered_the_same_key`, `rekey_state_survives_restart`, `revoked_device_with_pending_rekey_is_refused` and the extended `redeem_decides_again_on_records_that_moved_while_unlocked` (`server.rs`); the `hs_rekey` transport tests (`packages/e2e/src/transport.test.ts`: ack only after the key is stored, no ack when the store fails, the new key on the next handshake, never surfaced to the app); interop scenario 10 (`tools/e2e-interop.mjs`, real binary + TS client: the QR key is refused after the ack, the rotated key connects, a client that ignores `hs_rekey` keeps working).

**Residuals.**

- *The window before the first ack.* Until the paired phone's ack lands (normally within a second of its first connection), anyone holding the QR's PSK proves the current key, connects as the device and is sent the same `K_dev`. If an attacker redeems the QR first and acks, the real phone fails its first connection with a terminal deny ("Access denied"). That is visible, and the remedy is to revoke the device and pair again. Promotion does not close sessions opened under the QR's PSK before it: such a session stays up until it disconnects, and revoking the device (4003) ends it.
- *No forward secrecy.* A passive observer who also holds the QR's PSK and records the first session can derive that session's keys (the PSK plus the plaintext salt and client nonce) and read `K_dev` out of the sealed `hs_rekey` (ADR-011 scope note in `crypto.rs`). Rotation stops a later replay of the QR, not an attacker who had both the QR and the wire at pairing time.
- *Clients without rotation support* never ack: their device keeps the QR's PSK, and the QR stays a credential, until the phone is re-paired with a rotating app. Devices paired before this change have no pending key and are never rotated; re-pair them to get a device key.

The paired phone never used the pre-session snapshot. Evidence: `remote_posture_gates_commands_until_the_session_is_handshaken` (pre-session hello refused with no snapshot; sealed hello returns it). Original memo follows. **Memo (2026-10-24):** Question: **what should a pre-session `Hello` at remote posture return?** Finding 2 (§3.10) shows the current behavior — full `snapshot()` in plaintext to a token-holder before any PSK handshake — conflicts with ADR-013's "connection-admission credential only / counters-only residual" wording, while checklist row 1.2 and the README *expect* the token-only snapshot (read-only dashboard + admission). Two coherent options: **(A) keep the current snapshot-on-hello** — treat the transport token as a legitimate *read* credential for a dashboard, reconcile ADR-013's wording to say "admission + read-only state, never commands" (D2 still gates all command execution behind the PSK session), and update ADR-013; the residual is that a stolen token exposes current state (hosts/addresses, session titles, permission prompts, activity text) even without the PSK. **(B) gate the snapshot behind the session** — make remote-posture `Hello` return a counters-only or empty ack (like `/health`), forcing a paired device to handshake before reading state, matching ADR-013's stricter reading; cost: it changes checklist row 1.2 and the README "full snapshot on hello" promise, and a token-only monitor/dashboard loses read access. **Recommendation: (A)** — it matches the shipped product intent (checklist 1.2, README, the mobile client's own flow), keeps D2's security boundary intact (commands still require the PSK session, so the exposure is read-only state, not execution), and is the conservative *no-wire-change* direction; ADR-013's wording should be amended to make the read-scope explicit rather than the code silently tightened. Reserved to product owner (same ratification gate as D4); not gated in code pending that decision.
