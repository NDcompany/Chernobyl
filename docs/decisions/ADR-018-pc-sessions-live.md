# ADR-018: Claude Code sessions running on the PC, live on the phone (mirror, hook approvals, fork)

**Status:** Accepted 2026-11-12 (owner-delegated). Built on main.
**Relates to:** ADR-015 (live sessions, §10 "Claude session history", T1-T11), ADR-017 (composer), threat model `PHASE5-THREAT-MODEL.md` §3.12, `docs/PRIVACY.md`, `docs/INTEGRATIONS.md`, `apps/mobile/DESIGN.md`.

## 1. Context

ADR-015 §10 lists every Claude Code session on disk in an allow-listed workspace and lets the phone continue an idle one with `--resume`. A session that a terminal or the VS Code extension is writing right now (its JSONL changed in the last 2 minutes, `IN_USE_MS`) was shown but frozen: its history stopped at subscribe time, prompts were refused, and its permission prompts could only be answered at the PC. The owner wants every session on the PC usable from the phone, including the ones already running.

Three facts make that possible without attaching to another process:

- The CLI appends each entry of a session to `<config>/projects/<cwd>/<id>.jsonl` as it happens (user prompts, assistant blocks with `stop_reason`, tool results). The same `Driver` that decodes history can decode the tail.
- Claude Code runs `PermissionRequest` **command hooks** for every tool call that needs a decision. Documented shape (code.claude.com/docs/en/hooks, read 2026-11-12): stdin `{session_id, transcript_path, cwd, permission_mode, hook_event_name: "PermissionRequest", tool_name, tool_input, permission_suggestions?}` (no `tool_use_id`); stdout `{"hookSpecificOutput": {"hookEventName": "PermissionRequest", "decision": {"behavior": "allow" | "deny", "message"?, "interrupt"?, "updatedInput"?, "updatedPermissions"?}}}`; exit 0 with no JSON means no decision, so the normal flow continues; the default command-hook timeout is 600 s; "hooks run alongside" a host's own prompt and "whichever decides first applies".
- `claude --resume <id> --fork-session --session-id <new>` is accepted by CLI 2.1.322 (the CLI refuses `--session-id` with `--resume` unless `--fork-session` is set; checked with no API call). The fork gets the id we chose, so the companion knows it before the first frame, and the original file is never written.

## 2. Decision

### 2.1 Live mirror (`claude_history::Tail`, `claude_runtime` mirror thread)

- `replay(…, live)` returns the ops and a `Tail` positioned after the last whole line it read. With `live`, the last turn is left open and its tools keep their status; otherwise it is closed as before.
- The first subscriber of a listed session that is in use gets the replay, then a `claude-mirror` thread polls the file every 750 ms (`Timing::mirror_every`) and pushes what each poll adds through the same `Driver` path (`feed`, shared with replay). An assistant entry whose `stop_reason` is not `tool_use` ends the turn, so the working indicator stops when the PC's turn ends.
- Bounds per poll: at most 256 KiB read (`TAIL_POLL_BYTES`), at most 200 ops returned (`TAIL_OPS`, newest kept). A line still being written waits for its newline; a line over 4 MiB (`LINE_MAX`) is skipped whole and never buffered. A file that shrank, or whose first 256 bytes changed (replaced), is followed again from near its end after a notice. Every op goes through the hub, which redacts and caps as everywhere.
- The thread stops when nobody watches the session (`hub.is_subscribed`), when it leaves the list, when the companion stops, or when the file has been quiet for `IN_USE_MS` (then the open turn closes and the session stops being live). The stop decision is taken under the state lock that `hydrate` checks, so a subscriber arriving at that moment either sees the running mirror or starts a new one.
- `Session.livePc: true` (new optional field) marks a session written in the last `IN_USE_MS`. Discovery sets it on the probe cadence (15 s); a mirror sets it on the first new bytes and clears it when the file goes quiet; each change is a `session_updated`.

### 2.2 Approvals from the phone for PC sessions (the hook bridge)

- `chernobyl-companion.exe --hook permission-request [--timeout <s>] [--config <path>]` is the command hook. It reads the hook JSON on stdin (1 MiB cap), reads the companion config without ever writing one (`config::read_config`), checks that a companion holds this data directory's `companion.lock` (a sharing violation on a read-only open; the control key goes nowhere else), and POSTs the stdin to `127.0.0.1:<diagnostics port>/hooks/claude/permission?wait=<ms>` with the control key header. On `200 {"behavior": …}` it prints the documented decision JSON. On anything else (no config, no companion, wrong key, 204, timeout, any error) it prints **nothing** and exits 0, so Claude Code asks on the PC as usual. It never exits non-zero.
- The route (loopback diagnostics listener only, control key required, Origin refused, body ≤ 1 MiB) answers 204 at once unless: the event is `PermissionRequest`, a Claude live runtime is attached, at least one client is connected (a phone that is not there cannot answer, so the PC is not held), the cwd canonicalizes into an allow-listed workspace (T11), the session id is a UUID the companion does not drive itself (its own sessions answer through stdio), the tool is not `AskUserQuestion` or `ExitPlanMode` (they need `updatedInput`, i.e. the PC's own dialog), and fewer than 16 hook requests wait.
- Otherwise the runtime builds a normal engine `PermissionRequest` through `claude_live::permission_request` with `suppress_always_allow_rule`, so the options are exactly **Allow** (approve-once) and **Deny** (reject, with a reason the model sees). No suggestion, rule or mode change is ever offered on this path. It carries `fromPc: true` (new optional field), and its `expiresAt` is the hook's wait plus 2 s (the engine keeps that instead of its 24 h runtime TTL). The engine stays the G2 authority: it validates the decision (pending, revision, option) before the runtime hands it to the waiting request.
- The route holds the HTTP request open, checking every 250 ms. Phone decision: 200 with `{"behavior":"allow"}` or `{"behavior":"deny","message":…}`. Wait over (default 120 s, at most 600 s): the request is resolved `expired`, 204. The hook's socket closes first (Claude Code cancelled the hook because the PC answered, or the session moved on): resolved `stale`. A decision for an ended request is refused with "This request was already answered on the PC" or "This request timed out; the PC asked again there"; the last 32 such ids are kept for that answer.
- **Installation is explicit.** `--install-hooks` adds exactly one entry to `%USERPROFILE%\.claude\settings.json` (or `CLAUDE_CONFIG_DIR`): `hooks.PermissionRequest[] = {"hooks": [{"type": "command", "command": "\"<exe>\" --hook permission-request --timeout 120 --config \"<companion.json>\"", "timeout": 150}]}` (paths with forward slashes, so Git Bash and cmd both run it; a path with `"`, `$`, `` ` ``, `%` or `!` is refused). It backs the file up to `settings.json.chernobyl-backup` first, keeps every other key and hook, writes through a temp file and a rename, is idempotent (an identical entry leaves the file untouched), replaces an older entry of ours instead of adding a second, and refuses invalid JSON or an unexpected `hooks` shape without touching the file. `--uninstall-hooks` removes only our entry (and the `PermissionRequest` list or `hooks` object only if that leaves them empty). `scripts/setup-windows.ps1 -PhoneApprovals` calls `--install-hooks`. The companion never writes the file on its own.

### 2.3 Continue on the phone: fork

- `submit_prompt` takes an optional `fork: boolean` (TS and Rust validators share `composer-*.json`; anything but a boolean is refused). Codex, OpenCode and both mock engines refuse `fork: true`.
- For a session listed from disk (in use or not), the Claude runtime picks a new UUID and spawns `--session-id <new> --resume <old> --fork-session` in the recorded cwd (re-checked against the allow-list), under the same rate limit and `maxSessions` slot as `create_session`. The new session (`forkedFrom: <old title>`, new optional field) first gets the old session's history in its own transcript, then a notice "Forked from “…”; the PC session is unchanged", then the prompt. The ack's `sessionId` names the new session; a later respawn of the fork resumes the fork itself. A session the companion drives is not forked ("send a normal prompt").
- A plain prompt to a session in use is still refused (T10, text now "…continue it there, or fork it to continue on the phone"). Idle sessions still resume in place.

### 2.4 Phone

- Sessions list: a "Live on PC" tag (success dot, black outline) replaces the status pill for `livePc` sessions; a forked session shows "Forked from “…”".
- Conversation: for a `livePc` session the header shows the tag, and Stop, mode, model, rename and End are hidden (none of them can act on another process). The composer's placeholder reads "Continue on phone (fork)…" and its one-line hint says "Live on PC: sending forks it into a new session here; the PC session is untouched"; on the ack the screen is replaced by the new session. A forked session shows the "Forked from" line.
- Approvals from PC sessions are ordinary approvals: the Approvals tab, notification ("Approval needed (PC session)") and the conversation's standalone card ("Approval needed · from a PC session"), with Allow and Deny only.

## 3. Verified and assumed

- **Verified live** (`tests/live_hook.rs`, ignored, CLI 2.1.322, Haiku): `claude -p` in a temp workspace with the hook from a `--settings` file made by `install_hook` asked to Write; the binary's `--hook permission-request` reached the in-process companion, a connected client allowed it, and `hello.txt` was written. $0.0062. The settings file is passed with `--settings` rather than a temp `CLAUDE_CONFIG_DIR` because the CLI's sign-in lives in the real config dir and the test never copies it. This also shows the shell-form command line works on Windows.
- **Assumed, not verified:** in an interactive terminal or VS Code session, Claude Code shows its own dialog while the hook runs and cancels (kills) the hook when the PC answers first. That is what the docs say for hosts ("whichever decides first applies"); it cannot be exercised headless. If the CLI instead waited for the hook before showing its dialog, the PC prompt would appear only after the hook's timeout (120 s by default; `--install-hooks --timeout <s>` shortens it). If the CLI let an orphaned hook live on after the PC answered, a later phone tap would be accepted by the companion although the CLI ignores it; the phone would show "approved" for a request the PC had decided.
- The mirror's turn boundaries rely on `stop_reason` in the transcript's assistant entries (`end_turn`, `tool_use`, … seen in real transcripts on this PC). Queued prompts (`queue-operation`) and other entry types are ignored, like in history.

## 4. Consequences

- A PC session costs one thread and one 750 ms poll while a phone watches it; nothing while nobody does.
- With the hook installed, every permission prompt in an allow-listed workspace is mirrored to a connected phone and held up to the timeout; prompts outside the workspaces, or with no phone connected, are untouched.
- Not done: answering `AskUserQuestion` / plan approval from the phone for PC sessions, persistent rules through the hook, interrupting a PC session from the phone, and showing what the PC answered (the phone only learns that it did).
